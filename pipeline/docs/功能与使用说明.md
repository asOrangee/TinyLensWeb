# 功能与使用说明

用户直接调用 `lens-model-orchestrator` skill，并提供输入目录、要分析的 lens ID 列表和输出目录。skill 按顺序处理每个 lens，并在输出目录下建立对应的结果目录，完成后生成唯一的 `summary.csv`。

Python 提供以下无状态操作：

```bash
lens-agent preflight --lens-dir INPUT/LENS --output-dir OUTPUT/LENS
lens-agent inspector votes --output-dir OUTPUT/LENS --response VOTE_0.json --response VOTE_1.json --response VOTE_2.json
lens-agent inspector synthesis --output-dir OUTPUT/LENS --response SYNTHESIS.json
lens-agent mask --output-dir OUTPUT/LENS --inspection OUTPUT/LENS/preflight/synthesis.json
lens-agent stage --lens-dir INPUT/LENS --output-dir OUTPUT/LENS --stage a --attempt 0
lens-agent review context --output-dir OUTPUT/LENS --stage a --attempt 0
lens-agent review adjudicate --output-dir OUTPUT/LENS --stage a --attempt 0 --response RESPONSE.json
lens-agent attempt promote --output-dir OUTPUT/LENS --stage a --attempt 0
lens-agent rerun prepare --output-dir OUTPUT/LENS
lens-agent summary --output-dir OUTPUT
```

运行阶段时会自动检查输入、生成配置并验证准备文件，专家只需调用 GPU 运行命令。
`stage --prepare-only` 统一完成启动前准备，取代原 `--check-input`；它可能写入配置，
但不申请 GPU、不开始拟合。等待 GPU 后，程序会再次检查，然后才记录正式开始。

缺配置或准备中断可以自动恢复。输入缺失、权限不足或正式配置损坏会返回
`preparation_blocked`（退出码 2），操作记录保存在结果目录的 `.operations/` 中，
不会直接登记 `human_review`，也不消耗科学重试次数。修正条件后可运行同一个 attempt。
`busy`（退出码 75）表示已有进程正在准备或计算，应等待。已有结果直接返回，已启动却
中断的计算仍按原规则处理。程序不覆盖已有正式配置；中断留下的临时准备目录作为证据保留。
批次中若仍有准备受阻的 lens，应明确报告未完成，不生成它的终止性汇总。
独立 `attempt prepare` 仍可用于开发，但正常专家流程不需要单独执行它。

`preflight` 同时生成给三个独立 `system_inspector` 的中央两联图 `preflight_2panel.png`、供人工辅助检查的六宫格 `preflight_6panel.png` 和 `segmentation.fits`，并在 `run-manifest.json` 中固定 Pipeline Release。唯一权威的 segmentation 由正向 VIS 图像中至少 5 个相连且达到 3σ 的像素形成，并在同一阈值上拆分多峰结构。两联图和六宫格绘制完全相同的 3σ segment；两联图左侧是无标注 J/Y/VIS 彩图，右侧使用白色单色边界、黑色描边和黄色 ID，不让 segmentation 颜色被误解为真实天体颜色。三个 Inspector 只能看到同一两联图，彼此看不到结果；图像在固定 4″ 圆的每条边外额外保留一个像素（默认 0.1″），使 Inspector 能完整登记右图显示的 segment。

三份响应全部合法后，`inspector votes` 将它们一起保存到 `preflight/inspector-votes/`。随后只读的 `preflight_synthesis_expert` 仅阅读三份文字报告，不接收任何 preflight 图像。最终 `disposition` 和每个 `contaminant_id` 都必须获得至少两票；单票 ID 被排除。`model` 的 `theta_E_hint` 必须完整选自多数 `model` 票之一，`human_review` 的 hint 必须为 `null`。`inspector synthesis` 只验证这些规则并登记 `preflight/synthesis.json`，不会替专家计算或改写结果。之后 `mask` 写出唯一权威的 `preflight/inspector.json`；仅 `model` 会生成建模 mask，mask 中圆外 4″ 和最终 Non-Lens Segment 的 3σ 像素为 1，不做膨胀，也不恢复低于 3σ 的外翼。单 deflector 系统的 canonical `model` 允许固定 A–M3 workflow 运行，即使 preflight 形态解释不唯一。

用户明确要求“重新分析”“重跑”或“从头开始”某个 lens 时，Orchestrator 先调用 `rerun prepare`，把该 lens 的当前结果目录整体改名为 `_archive/<lens_id>_old_<N>`；`N` 始终取该 lens 现有最大编号加一，不填补现有归档之间的空号，流程也不会删除归档。随后仅对该 lens 从 `preflight` 开始全新运行，不继承旧 mask、attempt、审核、Accepted Stage Head、retry 预算或旧 Pipeline Release，同一批次的其他 lens 不受影响。`summary.csv` 完全跳过 `_archive/`。用户明确要求“继续”或“恢复”时不归档，而是沿用当前运行的 Accepted Stage Heads；若当前结果已存在而措辞未区分两者，Orchestrator 先询问而不移动目录。自动整体重跑允许任何 Pipeline Release 的有效 Lens Run Manifest；缺失、无法识别、含符号链接或旧格式目录会直接拒绝。所有会写入结果的命令均拒绝 `_archive/` 及其子目录。

每次运行都写入独立的 `attempts/<stage>/<N>/`，其中包括完整 `effective-config.json`、pkl/FITS/JSON 科学产物、PNG 诊断图、manifest、stage result、review 和 decision。接受与拒绝的 attempt 都保留；一旦生成 `stage-execution.json`，该 attempt 即封存，不能覆盖重跑。Hard Gate 检查命令成功、必要产物、有限数值，以及 M0 精细网格最优点是否在边界。

A、B、M0、M1、M2、M3 各自由一个贯穿当前 `lens × stage` 全部 retry 的 Stage Expert 负责。Expert 驱动当前 stage 的 prepare、物理运行、科学审核、局部调参和 promotion；在自动化 Lens Run 中，所有物理运行都通过统一 GPU Stage Runner 调用 `lens-agent stage`。Runner 在每次物理运行前等待并锁定一张空闲 GPU，通过 `CUDA_VISIBLE_DEVICES` 让 JAX 只看到该卡，并在进程结束时释放锁；Expert 本身不查询或分配 GPU。A、M1、M2、M3 各有独立科学说明和严格 schema；Stage B 也有独立 schema，并通过 `none/parameters/selection/uncertain` 证据让 Python 推导决定。M0 Expert 只判断 source grid 是否截断了从内部连续到边界的相干亮度，不审核质量残差、质量模型或一般 source 形态。

Stage A 只向 M0 提供后验中位数 source center。M0 初始使用以此为中心、外边界 `±0.8 arcsec` 的 `80×80` grid，source pixel 固定为 `0.02 arcsec`。每个 M0 attempt 写入唯一权威的 `artifacts/source_grid_spec.json` 和专用的 `diagnostics/stage_m0_source_grid.png`。若 Expert 确认真实截断，Python 按固定顺序扩展到 `±1.0`（`100×100`）或 `±1.2 arcsec`（`120×120`），并完整重跑 M0；Expert 不能自行选尺寸。证据不确定或 `±1.2 arcsec` 仍截断时转 Human Review。M0 接受后 grid 被封存，M1–M3 不得改变或回滚；M1/M3 若发现新的真实截断或无法区分截断与边界病态解，也只转 Human Review。grid JSON、attempt 配置、source 数组形状或 template 坐标不一致属于运行完整性错误，不做自动修复。

`review adjudicate` 是无状态的 Python 登记裁决：它重读当前 attempt，检查 Hard Gate、审核格式、stage 专属词汇、Tunable Catalog、参数旧值和新值、warning 谱系及 retry 预算，然后规范写入 `review.json` 和 `decision.json`。`decision.json` 同时记录依据文件的 SHA-256 指纹；依据文件后来被改动时，不会被误当成同一次重复登记。它不判断图像好坏，也不决定下一 stage。retry 次数从已完成 attempt 的正式证据重算，不维护独立计数文件。无法通过白名单参数修复时，Expert 可记录不可自动执行的开发建议并转人工审核，不能在当前 Lens Run 中修改 Python。

每个 attempt 在物理运行开始前先写入 `stage-execution.json`，从这一刻起封存。正常结束后再写入 `stage-result.json`；如果进程中途退出，登记员会核对这个启动记录并转人工审核，不会在同一 attempt 上重复运行。

Stage B 的 selection 单独存为绑定当前 component catalog 的 `arc-component-selection.json`，不属于通用 config；参数改变会使旧 selection 失效。审核响应格式错误可在同一 session 中更正两次，不会运行模型或消耗科学 retry；无效回答不写入结果目录。

retry 只能读取紧邻上一个 attempt 已正式登记的 `review.json` 和 `decision: retry`，再生成下一个完整 config；`attempt prepare` 不再接受外部审核回答。`accept` 后，promotion 重新检查 Hard Gate、decision、config 和 manifest，并原子写入 `accepted/<stage>.json`；只有 Accepted Stage Head 具有推进权。Stage B 在初始 attempt 后独享 10 次 retry；A、M0、M1、M2、M3 每个 stage 最多 retry 5 次，并继续共享每个 lens 合计 15 次的预算。M0 每次 grid 扩展同时消耗 M0 和共享物理 stage retry 预算。

活动 workflow 为 `A → B → M0 → M1 → M2 → M3`。M0–M3 使用 Stage A 保存的 lens-light model，`feature_mask.fits` 只表示 lensed-source support。旧 Stage-L workflow 的输出目录仅作为历史证据保留，不能在新 workflow 中续跑；请使用新的输出目录。

具体案例中提炼出的科学审查经验收录在[建模经验](lessons/README.md)中。这些经验用于帮助 reviewer 识别物理错配，不会改变 Hard Gate、重试预算或基线 pipeline。

生成产物不应提交到仓库；请将输出目录放在仓库外，或使用已被忽略的 `output/` 目录。
